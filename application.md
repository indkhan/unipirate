# How the application works

Current state: auth + full data model (schema, RLS, seed) + admin rule/course review workspace + the pure rule engine (`lib/engine`) + the public multi-step eligibility checker (`/check`) with designed anonymous shareable results (`/result/[id]`) + the strict-RAG AI assistant ("Ask") on the dashboard.

## Routes

- `/` — public v0.1 landing page (`app/(public)/page.tsx`) based on the Wayfinding design handoff. It explains the sourced eligibility product, shows the application route, and lets visitors start the login-free checker by certificate country. The selected country is carried into `/check`; sign-in remains a quiet secondary navigation action.
- `/check` — public, no login (`app/(public)/check/`). First-time checker: one question per screen, option cards, back navigation with persisted answers, mobile-first (390px) Wayfinding styling (tokens in `app/globals.css`, fonts loaded in `app/layout.tsx`). The header shows only the current step number while dots carry branch-aware progress, avoiding shifting "X of Y" totals as later questions unlock. Partial answers and the current step are saved to session storage per prefilled certificate country, so refreshes restore the in-progress flow; advancing pushes same-page history states so the browser Back button steps through prior questions before leaving `/check`. The first checker question is certificate country ("Where did you finish school?"); homepage country cards prefill that answer and open the checker on the second question, with Back revealing the prefilled country step. Nationality offers the three supported launch countries plus "Another country" = `other`, so unsupported passports can be answered honestly. The visa-application-country question ("Where will you apply for your German visa?" — options: the three supported countries plus "Another country" = `other`) is asked right after nationality; it feeds the `visa_application_country` fact that APS rules are scoped on (APS depends on the German mission's jurisdiction, not nationality — verified against aps-india.de/faq and the German Embassy Riyadh/VFS student-visa checklist). The existing-APS-certificate question is skipped when the visa is filed from Saudi Arabia (no APS on the Riyadh checklist). Curriculum type is asked before the board (CLAUDE.md rule 5) and routes to national-board vs GCE question branches; for Master's applicants the curriculum copy clearly says Master's guidance is limited and only verified rules will be confirmed; national-board Class 12 percentages are validated inline and must be 0–100 before Continue is enabled; GCE asks awarding body plus per-subject A-Level/AS/grade rows, prevents duplicate subjects from completing the step, and derives 13 vs 12 school years from those subject levels instead of asking a separate schooling-years question; IB/other skip curriculum detail and yield honest unknowns. Pure flow logic (zod `AnswersSchema`, `visibleSteps`, `withAnswer`, `buildProfile`, GCE subject catalog) lives in `app/(public)/check/steps.ts` and is unit-tested against engine personas #1/#11 in `app/(public)/check/__tests__/steps.test.ts`. Submit (`actions.ts` server action) validates answers, builds the engine `Profile`, evaluates against published DB rules, stores the normalized answers and result in a shareable `checks` row, and redirects to the result. Anonymous submissions receive a 256-bit HttpOnly owner token whose SHA-256 hash is stored with the check; logged-in submissions also immediately upsert `profiles.answers`, mark the check as claimed by that user, and therefore update dashboard tasks on the next dashboard sync. PostHog events: `check_started`, `step_completed` (`{step, question}`), `check_completed` (`{check_id}`).
- `/profile` — authenticated-only (`app/(app)/profile/page.tsx`). All-in-one saved profile editor for users who already completed the checker. It loads `profiles.answers`, shows every currently relevant answer at once, lets the user change any answer, and reuses the same `submitCheck` server action to re-evaluate, save the updated profile, and refresh dashboard task generation. Users without a valid saved profile are sent to `/check`.

- `/result/[id]` — responsive public shareable result (`app/(public)/result/[id]/`). Malformed result IDs 404 before any database lookup; well-formed unknown UUIDs also 404. Mobile and tablet use a compact single-column Wayfinding layout; desktop uses a 60/40 verdict-route/supporting-information grid. The stored result drives sourced verdicts, a personalized route, up to five visible documents, honest unknowns, and an intake-aware empty timeline that never invents dates; selected winter intakes keep the German semester label (`2026/27`) on the result page. The route model starts at "Confirm eligibility" for unknown paths and "Review alternatives" for insufficient paths, instead of marking eligibility complete. The profile summary uses readable board/curriculum labels and shows "Master's applicant" for Master's checks instead of raw enum badges. Verdict rows and "confirm whether X applies" unknowns are display-filtered for relevance (`buildVerdicts`/`visibleUnknowns` in `result-model.ts`): dMAT (an APS-India Master's test) is hidden for Bachelor's applicants and non-Indian certificates, TestAS (an undergraduate aptitude test) is hidden for Master's applicants — but a flag that evaluated to "required" is always shown; the engine still evaluates everything. Verified rules receive tappable green source stamps; beta rules use amber source treatment, and Pakistan/Saudi profiles carry a beta-country warning. Public visitors see shared-result messaging, anonymous owners see the single save/signup CTA, and claimed owners see saved confirmation. Copy, WhatsApp, and Telegram share the canonical result URL. After authentication, `?claim=1` exchanges the originating browser's owner token for an atomic, idempotent profile claim and then removes the query parameter. PostHog events: `result_viewed` (`check_id`, viewer, country, path; once per tab session), `result_shared` (`check_id`, channel), and `signup_from_result` (`check_id`).

- `/login` — public (`app/(public)/login/page.tsx`). Full Wayfinding-styled account access screen with email/password sign-in, email/password account creation, email magic link (Supabase OTP), Google OAuth handoff, forgot-password email, and reset-password mode. The client form uses one in-app validation path for every mode (including magic-link and forgot-password email-only flows), trims email addresses before auth calls, and maps Supabase failures to user-safe messages instead of showing raw API errors. `mode=signin|signup|magic|forgot|reset` controls the active panel; recovery links return to `/login?mode=reset` after `/auth/confirm` verifies the Supabase token. Google OAuth remains optional and can stay disabled in Supabase.

- `/dashboard` — authenticated-only (`app/(app)/dashboard/`), replaces the old `/hello` placeholder (all post-login redirects and proxy protections now point here). On every server render it runs `syncDashboard(db, user.id)`: saved checker `answers` are converted back to an engine `Profile`, published rules are evaluated, application rows are auto-created (`ensureApplications`) for the user's non-rejected imported courses (`getMyCourses`, keyed on `created_by`), and generated tasks are reconciled idempotently. The header has an account dropdown (Dashboard, Profile, Admin when relevant, Sign out) and a route line derived from the latest engine result: the APS station is shown only when `result.aps === "required"` and is not marked complete just because the profile exists. Global tasks come only from rule `stepsDetailed`; per-university tasks come from each imported course's verbatim `deadlines[]` and `requirements[]`. Generated tasks persist in `tasks` with `task_key` (`rule:<ruleId>:step:<order>`, `app:<applicationId>:deadline:<hash>`, `app:<applicationId>:req:<hash>`). The sync upserts only changed/new generated fields (`title`, `due_date`, `application_id`, `generated_from_rule_id`) and never writes `done`, so completed checkboxes survive reloads. Stale generated tasks are deleted only when `done=false`; stale done rows are kept invisible and can revive if the rule/course obligation returns.

  The page renders one merged plan organized Now / Next / Later plus a calendar view, with a Done section that keeps completed tasks visible so users can uncheck them and bring them back. Pending tasks can be dragged between Now, Next, and Later; the choice is stored on `tasks.preferred_bucket` so user organization survives refreshes while due dates and generated facts remain unchanged. Users can also add simple manual tasks (`task_key = null`) with an optional description, optional source URL, optional due date, and optional application attachment; manual task editing reopens the same dialog with the saved values prefilled, while generated rule/course tasks remain source-controlled and only expose the done toggle. Deadlines are always displayed verbatim from the source page; parsed ISO dates are used only for deterministic sorting, bucketing, and calendar dots. Calendar view has month navigation beside the month/year label, and clicking a dated day filters the list to the tasks on that day. Each tracked course creates at most one generated "Submit application" task. The selector uses the profile's chosen intake first: DAAD wording such as "of the year for the winter semester" or "previous year for the summer semester" is converted into the matching deadline date, and weaker month-only lines such as "15 May" / "15 November" are filtered to the likely winter/summer line without inventing a date. If the source does not expose intake-specific wording, it falls back to the next upcoming parsed deadline. The header shows a compact route line and nearest pending deadline, and links users without a saved profile back to `/check` so global APS/visa/blocked-account tasks can be generated. The horizontal applications rail shows one card per `applications` row with an inline native status select (`planning`/`applied`/`admitted`/`rejected`) backed by `updateApplicationStatus`; submitted/admitted applications stop generating submission/requirement tasks on the next sync. Removing a course deletes its application row (`deleteApplicationForCourse`, fixing approved-course rail ghosts) before `remove_my_course()` detaches or deletes the course. Both the empty-state CTA and the rail "+ Find courses" link now lead to `/courses` — URL import moved there. PostHog events: `course_imported` (`{method}`), `course_import_failed` (`{status}`) now fire from the finder.
- `/courses` — authenticated-only Course Finder (`app/(app)/courses/`, guarded by `proxy.ts` exact-match and a page-level redirect). Lists all approved courses (`getApprovedCourses`, name-ordered) in dashboard-styled cards with a client-side search box (course or university name) and degree/language/city `<select>` filters derived from the data; each card links to `/courses/[id]` and has an "Add to my dashboard" button (`addCourseToDashboard` server action → `ensureApplication` upsert) that flips to "On your dashboard". The "Add it by URL" bottom sheet (`add-course-sheet.tsx`) is a three-step flow: (1) URL only → lookup POST to `/api/courses/import`; (2) if the URL already has a course (DAAD language variants dedupe to the same id), show it with "Add to my dashboard" or "The page changed — submit an update"; (3) paste the Ctrl+A page text and submit — a fresh import, or an update submission carrying `conflictsWith`. PostHog events: `course_added_from_finder` (`{course_id}`), `course_update_submitted` (`{course_id}` of the disputed course), `course_imported` (`{method}`), `course_import_failed` (`{status}`).
- `/admin` — authenticated admin-only (`app/(admin)/admin/page.tsx`). `proxy.ts` redirects logged-out users to `/login` and non-admin users to `/dashboard`; the page and server actions repeat the same admin check. Admins can filter rules by `country_code` and `status`, edit country/rule JSON/source/status fields, one-click re-verify a schema-valid rule (`status='verified'`, `last_verified_at=now()`), edit pending course facts before review (core fields, location, description/content, plus tuition/deadlines/requirements JSON; saved corrections mark extraction as `manual`), approve/reject pending courses (the queue shows university_name and highlights AI-extracted field groups amber via `field_extraction`; conflict submissions are excluded from this queue), resolve conflicting courses (a "Conflicting courses" section shows each update submission side-by-side with the course it disputes, both editable via the shared `CourseEditForm`; "Keep existing" or "Replace with update" calls the atomic `resolve_course_conflict` DB function — see Data model), and inspect recent audit events.
- `/courses/[id]` — public course page (`app/(public)/courses/[id]/`). RLS decides visibility: approved courses are public, a pending course is visible only to its importer (with an amber "In review" banner), everything else 404s. Renders extracted facts — name, university, location, degree, teaching language, tuition, DAAD description/content in a collapsed toggle when present, verbatim deadlines (mono, signal), requirements checklist — plus a prominent route-blue "View the official course page" button with source domain and imported date.
- `POST /api/courses/import` — authenticated JSON API (`app/api/courses/import/route.ts`). Input: `{url, text?, conflictsWith?}` where `text` is the full Ctrl+A page text supplied by the user (the server never fetches or renders external pages). `normalizeUrl` canonicalizes any daad.de `/detail/<id>/` URL to the EN international-programmes URL so language variants dedupe to one course. Without `text` the call is a lookup: it returns the existing course for that normalized URL (`{course, deduped}`) without inserting anything. With `text` and no `conflictsWith`: dedupe against `courses.normalized_url` (a match links the course to the caller's dashboard and returns it; an invisible other-user pending row is caught via the unique-index duplicate error → 409) → deterministic DAAD label parser (`lib/courses/parse-daad.ts`) → OpenRouter `qwen/qwen3.6-flash` `generateObject` fallback (`lib/ai/extract-course.ts`) only for fields the parser missed, with verbatim-quote-only prompting → insert as `pending` with `extraction_method` (overall) and `field_extraction` (per field group: core/description/deadlines/requirements/tuition → library|ai). With `conflictsWith` (uuid of a visible existing course): dedupe is skipped and the row is inserted as a pending conflict submission carrying `conflicts_with`. Every successful import/dedupe also upserts the caller's `applications` row (`ensureApplication`), which is what puts the course on their dashboard. Garbage input (no name and no deadlines even after AI) → 422 with a useful message. Deadline/tuition/description values are stored verbatim from the page, never converted.
- `POST /api/assistant/chat` — authenticated streaming chat API (`app/api/assistant/chat/route.ts`, Vercel AI SDK UI-message stream). Flow: auth → zod-validate `{messages}` → daily quota check (20 questions/user/day, `countTodayAssistantQuestions`, UTC midnight reset) → log the question to `assistant_messages` *before* streaming (aborted streams still count) → `runAssistant` (`lib/ai/assistant.ts`). The assistant streams `openai/gpt-5.4-mini` via OpenRouter with `stopWhen: stepCountIs(6)`, `maxOutputTokens: 1024`, temperature 0, and three tools: `search_rules` (embeds the query with `openai/text-embedding-3-small` via OpenRouter → `match_kb_chunks` pgvector RPC, top 6), `get_user_context` (profile + applications-with-courses + tasks + derived next-due-task/status counts; authorization is the user's RLS session), and `web_search` (Tavily REST via plain fetch; pass 1 restricted to official domains — daad.de, aps-india.de, uni-assist.de, diplo.de, auswaertiges-amt.de, goethe.de, anabin.kmk.org — pass 2 general if empty; all results flagged `unverified: true`; missing/failed `TAVILY_API_KEY` degrades to an honest "web search unavailable" note). The country-templated system prompt (in = verified, pk/sa = beta with a beta caveat required per answer, other = uncovered) enforces the strict-source contract: answer ONLY from tool results; every factual claim carries an inline `[[rule:slug]]` or `[[web:url]]` marker; when sources don't answer, emit `[[unknown]]` plus the official source URL — refusing to guess is success. Markers (`lib/ai/markers.ts`, pure, client-safe) are parsed on finish to log the answer + citations to `assistant_messages`.
- **Assistant UI** — "Ask" slide-over on the dashboard header (`components/app/assistant-sidebar.tsx` + module CSS, ported from `design/Assistant.dc.html`; right-anchored 460px panel, full-screen ≤640px). Uses `@ai-sdk/react` `useChat` + `DefaultChatTransport`. Empty state offers 3 suggested questions; assistant bubbles strip markers for display and render: a green `VerifiedStamp` per `[[rule:slug]]` (`components/app/verified-stamp.tsx`; source URL/date resolved from any `search_rules` tool output in the conversation, falling back to the slug), the amber "Unverified — double-check" chip + links per `[[web:url]]`, and the dashed "Not in our verified rules" block for `[[unknown]]`. Each answer has "Report this answer" → `reportAssistantAnswer` server action (`app/(app)/dashboard/actions.ts`) → `answer_reports` with `{question, answer, citations}` context. Header shows `n/20 today` (server-passed initial count + client increments); at the limit the composer disables and the API returns 429.
- `/auth/confirm` — GET route that verifies magic-link `token_hash` and redirects to `/dashboard`.
- `/auth/callback` — GET route that exchanges the OAuth `code` for a session and redirects to `/dashboard`.

## Auth flow

`proxy.ts` (Next 16 middleware) runs on every non-asset request: it refreshes the Supabase session cookies via `@supabase/ssr`, redirects logged-out users away from `/dashboard`, `/profile`, and `/admin`, and blocks `/admin` unless `user.app_metadata.role === 'admin'`. Server code gets a Supabase client from `lib/db/server.ts`; client components use `lib/db/client.ts`. Password login uses Supabase email/password auth; account creation sends the user through Supabase email confirmation before they can rely on the account; magic links use Supabase OTP; forgot-password uses Supabase recovery email and then `auth.updateUser({ password })` from `/login?mode=reset`. Login, email confirmation, OAuth callback, and recovery flows accept only validated same-origin `next` paths, allowing the result CTA to return to `/result/[id]?claim=1` without creating an open redirect. Already-authenticated visits to `/login` redirect to the safe `next` path or `/dashboard`, except reset-password mode, which stays on the form so a recovery session can choose a new password.

- `components/app/posthog-provider.tsx` — initializes PostHog (if `NEXT_PUBLIC_POSTHOG_KEY` is set) with automatic pageview/pageleave capture; wraps the app in `app/layout.tsx`.
- `scripts/send-test-email.ts` — sends a test email through Resend (`pnpm email:test <to>`).
- Vitest (`vitest.config.ts`) with `@` alias; smoke test in `lib/engine/__tests__/`.
- `pnpm kb:embed` (`scripts/embed-kb.ts`) — rebuilds the assistant knowledge base: renders published (beta+verified) rules to readable text chunks (`lib/ai/kb.ts` `ruleToChunk`, unit-tested — intake indexes and `YYYYMMDD` date facts become human semesters/dates), merges the curated snippets from `scripts/kb.snippets.ts` (source of truth for `source_type='snippet'` rows; hand-lifted from `docs/research_findings.md` with source URLs + verified dates), embeds everything with `openai/text-embedding-3-small` via OpenRouter, and delete-and-reinserts `kb_chunks`. Rerun after rule changes or snippet edits.
- `pnpm eval:assistant` (`scripts/eval-assistant.ts` + `scripts/eval-questions.ts`) — the 20-question adversarial eval (categories: rules, out-of-scope traps, invented-fact traps, personal-context, web/current). Creates a throwaway user with a seeded India profile/tasks, runs each question through `runAssistant`, and fails unless every answer carries a citation marker or an honest `[[unknown]]` (personal-context answers are exempt from citation — they come from the user's own data), every trap refuses, and there are ≥3 honest unknowns. Latest run: 20/20, 13 unknowns.
- Env: `TAVILY_API_KEY` (optional) enables the assistant's `web_search` tool; without it the tool degrades honestly.

## Rule engine (`lib/engine`)

`lib/engine/evaluate.ts` — pure functions, zero I/O. `evaluate(profile, rules[]) → Result` where `rules` are rows in the `rules` table's jsonb shape (callers load them via `lib/db`; the engine never touches the DB). Eligibility logic lives entirely in the rule records; the engine only:

- **Derives facts** from the `Profile` while keeping nationality, certificate country, and visa-application country as distinct intake data. Only facts used by supported rules are derived; eligibility thresholds and effective dates remain in DB rule conditions.
- **Matches conditions**: a rule's `conditions` is a flat AND map of `fact: value` (equality) or `fact: {op, value}` with `eq/neq/gte/gt/lte/lt/in/nin`. A condition on a missing fact never matches. Draft or malformed rows are skipped; admin publishing rejects malformed conditions/outcomes and stamps the verification date.
- **Merges outcomes** into `Result`: `path` (direct | subject_restricted | studienkolleg | insufficient | unknown), `aps`/`testAS`/`dMAT` flags, de-duped `documents`, order-sorted `steps`, `stepsDetailed` (`order`, `text`, `ruleId`) for generated dashboard tasks, and `citations[]` (rule id + source_url + last_verified_at + status + supported result keys + claim per contributing rule). Per key, the most-specific matching rule (highest condition count) wins; an equal-specificity conflict returns `unknown` with all tied rules cited. No matching rule for a key → explicit `unknown` plus a "confirm with [official source]" entry in `unknowns` — missing data is a valid state, never guessed.

Tests: `lib/engine/__tests__/` — `personas.ts` (the 13 Part-E personas from `docs/research_checklist.md`), `rules.fixture.ts` (the same bootstrap candidates used by the seed), and `evaluate.test.ts` (persona, transition, international-curriculum, and engine-behavior regressions).

## Data model

Schema lives in `supabase/migrations/20260704094923_init_core_schema.sql`, with API-role grants in `supabase/migrations/20260704122600_grant_api_role_privileges.sql` (Supabase is cloud-hosted; apply with `pnpm supabase db push` against the linked project — never `db reset --linked`). Types: `lib/db/database.types.ts` (regenerate with `pnpm db:types`). All reads/writes go through the typed helpers in `lib/db/queries.ts` — no inline SQL/queries in components.

Tables:

- `countries` (code pk: in/pk/sa/de), `qualifications` (level enum school/bachelor/master, board_or_type; `country_code null` = international curricula like IB/GCE A-Levels, which route to their own rule tree), `universities` — public-read reference data, admin-write.
- `rules` — the eligibility engine's runtime source of truth: stable `slug`, display/filter `country_code`, `conditions`/`outcomes` jsonb, status, source metadata, and verified date. Public-read except drafts; only admins write. Bootstrap candidates are always inserted as drafts and never overwrite existing rows; only a human publishes them through `/admin`.
- `courses` — extraction target for pasted course URLs: extraction fields (name, `university_name`, location, degree, language, description, tuition/deadlines/requirements jsonb — deadlines/requirements are verbatim string arrays, tuition a verbatim string), `normalized_url` (dedupe key, unique via a partial index `where conflicts_with is null` so update submissions can coexist with the course they dispute), `conflicts_with` (self-FK, `on delete set null` — non-null marks a pending "the page changed" submission), `review_status` pending/approved/rejected, `extraction_method` library/ai/manual (overall), `field_extraction` jsonb (per field group library|ai), `created_by` (provenance only — dashboard membership is the `applications` row). Public-read where approved; owners read their own pending rows and insert forced to `pending`. `remove_my_course()` keeps approved courses public (sets `created_by = null`) and deletes the caller's own non-approved imports; the dashboard remove action first deletes the caller's `applications` row (`deleteApplicationForCourse`). `resolve_course_conflict(p_new_course_id, p_keep_new)` (security definer, admin-only) atomically resolves a conflict: keep-new repoints `applications` rows from the old course (skipping users who track both), deletes sibling conflict submissions plus the old course, and approves the update; keep-old repoints the submitter and deletes the update. Caveats: deletes are not audited (the audit trigger only logs updates), and tasks hanging off a deleted duplicate application die with it (tasks are unused in the UI today).
- `admin_audit_events` — append-only audit trail for `rules` and `courses` updates. Triggered at the database level by `audit_admin_update()` after every update, storing actor user id, table name, row id, action, old/new status, old/new row snapshots, and timestamp. Admin read-only via RLS; inserts are performed by the security-definer trigger function.
- `profiles` — one per user (pk user_id), `country_code` + `answers` jsonb (checker Q&A). Owner CRUD, admin read.
- `applications` (user × course, unique pair, status text) — THE user↔course dashboard link: `syncDashboard` upserts rows for the user's `created_by` imports, and the Course Finder / URL-dedupe upsert one directly (`ensureApplication`). `tasks` (`application_id null` = global task like APS; `description` = optional user-facing detail/notes; `source_url` = optional manual source/reference link; `preferred_bucket` = user's Now/Next/Later drag override; `task_key null` = manual task; non-null `task_key` = generated task identity; `generated_from_rule_id` links back to the rule that spawned it). Owner CRUD, admin read. `tasks` has a full unique constraint on `(user_id, task_key)` so PostgREST `upsert({ onConflict: "user_id,task_key" })` works; nullable keys remain available for manual tasks.
- `rule_reports` / `answer_reports` — "this info is wrong" feedback; `user_id null` = anonymous report from the loginless checker. Anyone may insert, reporters read their own, admin reads/resolves.
- `kb_chunks` (`supabase/migrations/20260706193410_add_assistant_kb.sql`) — the assistant's embedded corpus: `source_type` rule|snippet, optional `rule_id` (cascade), unique citation `slug`, title/content, `source_url`, `last_verified_at`, optional `country_code`, `embedding vector(1536)` (pgvector in the `extensions` schema). Public-read (only ever holds beta/verified content), admin-write; rebuilt wholesale by `pnpm kb:embed`. No ANN index — the corpus is <100 rows, exact scan; add hnsw past ~10k. `match_kb_chunks(query_embedding, match_count)` is a stable SQL function returning chunks by cosine similarity (`operator(extensions.<=>)` — the operator must be schema-qualified because of the function search path).
- `assistant_messages` — full assistant Q&A log: `user_id`, role user|assistant, content, `citations` jsonb (parsed markers on assistant rows). Owner insert/read (+admin read); indexed on `(user_id, created_at desc)`; the daily quota is the count of today's `role='user'` rows.
- `checks` — anonymous eligibility check records (`answers` + normalized `profile` + `result` jsonb). Anyone may insert and anyone holding the UUID may read only the shareable fields. Private ownership metadata stores an owner-token hash plus optional `claimed_by`/`claimed_at`; the raw token exists only in the originating browser's HttpOnly cookie. The authenticated-only `claim_check` database function verifies the hash, replaces the user's profile answers with the selected check, and records ownership in one transaction; `result_viewer` reveals only whether the current request is the anonymous owner, claimed owner, or public. Pre-ownership-migration checks stay shareable but cannot be securely claimed.

RLS is enabled on every table. The grant migration gives Supabase API roles the baseline table privileges needed for policies to run; RLS remains the user-facing authorization boundary, while `service_role` has full table privileges for seed/admin scripts. Admin = JWT claim `app_metadata.role = 'admin'`, checked by the `is_admin()` SQL helper; set it via the Supabase admin API. `updated_at` maintained by a shared `set_updated_at()` trigger. `rules` and `courses` updates also write `admin_audit_events` rows through audit triggers so status changes are recorded independently of the UI path.

Seed: `pnpm db:seed` (idempotent; needs `.env.local`) inserts reference data and 34 schema-validated draft rule candidates from `scripts/rules.bootstrap.ts`. APS rules are scoped by `visa_application_country`: `aps-india-national` additionally requires `visa_application_country: "in"`, and `aps-not-required-visa-from-sa` (`visa_application_country: "sa"` → `aps: not_required`, source: German Embassy Riyadh/VFS student-visa checklist) covers anyone filing the visa from Saudi Arabia regardless of nationality. Existing slugged rules are never overwritten. The process-step rules for APS India, uni-assist/VPD, blocked account, and India/Saudi visa appointments are seeded as drafts only; they do not affect dashboards until a human publishes them in `/admin`.

RLS test: `lib/db/__tests__/rls.integration.test.ts` runs anon/owner/admin assertions against the real project when `.env.local` (or env) provides the Supabase keys; otherwise it self-skips so `pnpm test` stays green.
